# Алгоритм анализа данных — Telegram Collector

## Обзор системы

Проект состоит из трёх компонентов, которые работают в цепочке:

```
[Chrome Extension]  →  [FastAPI / Telegram Bot]  →  [Отчёт пользователю]
  Сбор данных           Анализ (analyzer.py)          Форматирование
```

---

## Фаза 1 — Сбор данных (`content.js`)

Расширение Chrome внедряется на страницу `web.telegram.org` и парсит DOM.

### Что собирается с каждого поста:

| Поле | Откуда берётся |
|---|---|
| `text` | `.text-content`, `.bubble-content .message`, `.message` |
| `views` | `.message-views` или `.post-views` → `.time-inner[title]` → regex `Views: N` |
| `shares` | Тот же элемент → regex `Shares: N` |
| `time` | `.message-time`, `.time-inner`, `.time` |
| `reactions` | `.message-reaction` или `reaction-element` → emoji + счётчик; `page-bridge.js` переносит публичную модель реакции из MAIN world в безопасные `data-tgc-*` атрибуты, DOM/doc id остаются fallback |
| `links` | `a.text-entity-link` → тип: `mention` если `@`, иначе `url` |
| `hasMedia` | Проверяет медиа только внутри `.bubble-content`, исключая картинки реакций |
| `forwardFrom` | `.forwarded-name` |
| `hasPoll` | `.poll` |
| `comments` | `.comments-button` или `replies-element` → число из текста/`aria-label` |

### Дедупликация:
Каждый пост идентифицируется по `data-message-id`, `data-mid`, `data-id` или `data-post`. Дубли пропускаются через `Map`.
Пустые элементы (нет текста, нет медиа, нет реакций) тоже отбрасываются.

### Метаданные канала:
Собирается отдельно — название, количество подписчиков, описание, URL.

## Фаза 2 — Анализ данных (`bot/analyzer.py`)

Главная функция `analyze(data)` последовательно запускает 5 модулей + финальный скоринг.

---

### Модуль 1 — Просмотры (`analyze_views`)

**Что делает:** вычисляет статистику просмотров по всем постам.

**Ключевая метрика — CV (коэффициент вариации):**

```
CV = стандартное_отклонение / среднее_значение
```

CV показывает, насколько равномерно распределены просмотры:

| CV | Вердикт | Смысл |
|---|---|---|
| < 0.05 | `suspicious` | Слишком стабильно — признак накрутки ботами |
| 0.05–0.15 | `stable` | Стабильная, но живая аудитория |
| 0.15–0.40 | `normal` | Нормальная волатильность |
| > 0.40 | `unstable` | Очень непредсказуемые просмотры |

**Выбросы:** посты с просмотрами `> 3 × медиана` считаются аномальными.  
Медиана используется вместо среднего, чтобы устойчиво работать при наличии вирусных постов.

---

### Модуль 2 — Вовлечённость (`analyze_engagement`)

**Что делает:** измеряет, насколько активна аудитория относительно просмотров.

**Формулы для каждого поста:**

```
ER (engagement rate) = реакции / просмотры
Share rate           = репосты / просмотры
Comment rate         = комментарии / просмотры
```

Затем берётся **среднее по всем постам** (отдельно для каждой метрики).

**Охват подписчиков** (если известно количество подписчиков):

```
views_to_subs_pct = средние_просмотры / подписчики × 100
```

Если этот показатель > 80% — это физически невозможно при органическом росте и является сигналом накрутки.

---

### Модуль 3 — Реакции (`analyze_reactions`)

**Что делает:** анализирует разнообразие и распределение эмодзи-реакций.

**Энтропия Шеннона** (вычисляется для каждого поста):

```
H = -Σ (p_i × log2(p_i))
```

где `p_i` — доля каждого типа реакции в конкретном посте.

**Интерпретация энтропии:**
- **Высокая энтропия (H > 1.0)** → реакции распределены равномерно между разными эмодзи → живая аудитория  
- **Низкая энтропия (H < 0.5)** → одна реакция доминирует (например, 95% «👍») → подозрительно

**Вердикт аутентичности:**

| Условие | Результат |
|---|---|
| Энтропия > 1.0 И типов реакций ≥ 3 | `organic` — органично |
| Энтропия > 0.5 ИЛИ типов ≥ 3 | `neutral` — нейтрально |
| Иначе | `suspicious` — подозрительно |

---

### Модуль 4 — Расписание (`analyze_schedule`)

**Что делает:** определяет, как публикуются посты — по расписанию или хаотично.

**Метод:** для каждого поста извлекается время (часы + минуты), переводится в «минуты от начала суток».  
Вычисляется стандартное отклонение по всем временам публикации.

| Станд. отклонение | Тип | Смысл |
|---|---|---|
| < 30 минут | `cron-like` | Автопостинг — явно по расписанию |
| 30–180 минут | `scheduled` | Плановый постинг |
| > 180 минут | `organic` | Случайные, живые публикации |

Также находятся **топ-3 часа** с наибольшей активностью.

---

### Модуль 5 — Контент (`analyze_content`)

**Что делает:** рассчитывает процентный состав контента.

- **media_pct** — доля постов с медиа (фото, видео, документы)
- **forwarded_pct** — доля пересланных постов (чужой контент)
- **polls_pct** — доля постов с опросами
- **links_pct** — доля постов со ссылками
- **link_types** — разбивка ссылок: `mention` (@username) vs `url` (внешние)
- **avg_text_len** — средняя длина текста в символах

---

### Финальный скоринг — Оценка накрутки (`calculate_fraud_score`)

**Что делает:** агрегирует все сигналы в единый балл риска от 0 до 100.

Каждый подозрительный признак добавляет очки:

| Условие | Очки | Почему подозрительно |
|---|---|---|
| CV просмотров < 0.05 | +20 | Ненормально стабильные просмотры — боты |
| CV просмотров < 0.10 | +10 | Слегка подозрительная стабильность |
| Engagement rate < 0.1% | +20 | Люди видят, но почти никто не реагирует |
| Engagement rate < 0.3% | +10 | Низкая вовлечённость |
| Типов реакций < 3 | +15 | Монотонные реакции — ботовый паттерн |
| Энтропия реакций < 0.5 | +15 | Одна реакция заполняет всё |
| Пересланных постов > 40% | +10 | Канал в основном ретранслирует чужое |
| Выбросы просмотров (×3 медианы) | +10 | Аномальные всплески просмотров |
| URL-ссылки > 70% от всех ссылок | +5 | Высокая рекламная плотность |
| Охват > 80% подписчиков | +15 | Физически невозможно без накрутки |

**Итоговый риск:**

| Баллы | Уровень |
|---|---|
| 0–20 | ✅ Низкий |
| 21–45 | ⚠️ Умеренный |
| 46–70 | 🚨 Высокий |
| 71–100 | 🔴 Критический |

Максимум ограничен 100 через `min(score, 100)`.

## Фаза 3 — Вывод результатов

Результаты передаются двумя путями в зависимости от того, как запущен анализ:

### Путь А — Chrome Extension (popup.js)
```
getData → POST /analyze → renderResults()
```
- Данные отправляются на локальный Docker-контейнер (`http://localhost:8000/analyze`)
- Результаты отображаются прямо в popup расширения с графиками и прогресс-барами
- Кольцо fraud score окрашивается в цвет риска через `conic-gradient`

### Путь Б — Telegram Bot (bot.py)
```
JSON-файл → analyze() → format_report() → несколько сообщений в чат
```
- Пользователь присылает JSON-файл боту
- Бот запускает тот же `analyze()`, затем `format_report()`
- Результат разбивается на 7 блоков-сообщений: заголовок, просмотры, вовлечённость, реакции, расписание, контент, оценка накрутки

## Схема потока данных

```
web.telegram.org
       │
       ▼
 content.js (парсинг DOM)
       │
       │  {posts[], metadata}
       ▼
  popup.js / bot.py
       │
       │  POST /analyze  (или прямой вызов)
       ▼
  analyzer.py
  ├── analyze_views()        → CV, медиана, выбросы
  ├── analyze_engagement()   → ER, share rate
  ├── analyze_reactions()    → энтропия, топ-5 эмодзи
  ├── analyze_schedule()     → пиковые часы, тип постинга
  ├── analyze_content()      → медиа%, пересылки, ссылки
  └── calculate_fraud_score() → итоговый балл 0–100
       │
       ▼
  formatter.py / popup.js → отчёт пользователю
```
